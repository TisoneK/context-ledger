## ADR-1: Collaboration events are immutable JSON documents, v1 (2026-09-10)
- **Status:** accepted — shipped in core 0.22.0
- **Context:** markdown frontmatter events had a `none` sentinel, CSV-in-string fields, no version marker on a durable trail, and no machine validation; the light path needed to work identically solo and in collaboration.
- **Decision:** one `<id>.json` per event per `collab-event.schema.json` v1, written in a strict profile (fixed key order, one key per line, UTF-8 no BOM) so POSIX-sh readers need no JSON dependency; legacy `.md` events stay readable forever. Full design: `designs/collab-events-json.md`.
- **Consequences:** writers must escape bodies (backslash/quote/CR/LF) and emit all 14 keys; the trail-level state machine stays in `ledger-collab check`; future format changes bump the `schema` field and branch readers.

## ADR-2: The ledger self-hosts; vendored core tracks releases, not dev head (2026-09-10)
- **Status:** accepted
- **Context:** the protocol's home repo had no coordination surface — two maintainer sessions collided mid-release (flaws/log.md 2026-09-10). The repo now runs its own vendored `.context_ledger/`.
- **Decision:** after a release commit lands, the releasing session syncs the vendored core as its closing step — `sh .context_ledger/core/bin/ledger-sync update core` (source = this repo's own `core/`), verify, commit as `chore(ledger): self-host core <version>`. Between releases the board runs the last release; dev head isn't protocol until it ships. MAJOR bumps need the user's go-ahead.
- **Consequences:** sessions here follow the same check-in/claim/log discipline as any project (README "Working on this repo"); the manifest regen belongs to the last session to finish; one workstream at a time, or worktrees + the collab ceremony.

## ADR-3: The memory layout is an office — one live, unnumbered, frozen verbatim at close (2026-09-11)
- **Status:** accepted — shipped in core 1.0.0
- **Context:** session grouping (0.13.0) kept the live group as flat paths and condensed it into `history/group-<NNN>.md` on close, resetting roster and registry; resolved-but-unpruned durable-log entries and stale domain files leaked across group boundaries, and nothing nudged a close. The supervisor specified the inversion directly: one live office, numbered only when archived, frozen whole ("even the rosters stay intact — no trimming"), a permanent record per office so its accomplishments are never forgotten, and old layouts grouped into an office during sync.
- **Decision:** the live office is the unnumbered directory `memory/office/` (everything session-produced: roster, registry, notes, tasks, plans, flaws, inefficiencies, reviews); durable files (workflows/, collaboration/, system/, user/, overrides/, core.lock, secrets/) stay at the memory root and never rotate. `ledger-history close` moves the directory verbatim to `history/office-<NNN>/` (number derived from the records — no state file), writes the permanent record `history/office-<NNN>.md`, and seeds a fresh office from templates. No implicit carryover: the closing session re-seeds open threads explicitly. `ledger-gates checkpoint` warns when the office is full. Legacy flat layouts migrate during `update`/`migrate`. Full design: `designs/office-architecture.md`.
- **Consequences:** a new office cannot be misdirected by a previous office's leftovers — at the cost of ADRs and open flaws leaving the startup read at close (re-seeded only if still relevant; the permanent record is the bridge). Close is deliberate session work, not automation. Breaking layout change → MAJOR; every install migrates via `update --major`.

## ADR-4: Session reports are specified by voice, not by a mandated skeleton (2026-09-11)
- **Status:** accepted — shipped in core 1.0.4
- **Context:** every session report had to follow Executive Summary → Discovery Phase → Baseline Health → Findings → Fixes Applied → Open Items → Recommended Next Steps. The maintainer flagged the output as too complicated and robotic for the person who reads it; the skeleton optimized for archiving, not reading.
- **Decision:** Step 13 (both editions), `reviews/README.md`, and the feature-engineer overlay now specify the report's voice — plain sentences for the project's owner, what happened first, no form-speak headings — with a suggested flow (what happened → found → changed → still open → next) that sessions may reshape. A clean review is one plain line. The feature report keeps its substance list (design decisions, verified vs. not verified, open items).
- **Consequences:** reports will vary in shape between sessions (the `reviews/README.md` naming rules are unchanged, so files still sort and scan); "read the most recent report fully" remains how a session picks up prior work; severity labels survive only where a finding carries one.

## ADR-5: The office coordinates at a glance and bounds its own memory (2026-09-14)
- **Status:** accepted — shipped in core 1.1.0/1.1.1
- **Context:** supervisor PATCH, four related pain points: (1) a returning worker couldn't see at a glance how far each live peer had got or how to coordinate; (2) offices never closed on time — >S020 session lists leaked stale context into fresh offices; (3) the append-only logs (`sessions.md`, `flaws`, `inefficiencies`, `decisions`) accumulated "none this session" noise and repeated friction forever; (4) ledger vocabulary (a bug ID, `.context_ledger/` path) was leaking into vendored product code, dangling for downstream readers.
- **Decision:** (1) the roster gains `Status` (`Working`/`Done`/`Blocked`) + a one-line `Status detail` (stage reached / "Shipped: …" / blocker), edited in place; `ledger-mem check` warns on an empty Status cell. (2) A full office closes **at the door**: the worker whose check-in read finds `sessions.md` past `office_size` (default 20 → past S020) runs `ledger-history close` before the deep read; re-seeded entries carry the **work, never the closed office's session numbers/codenames**, and the fresh office restarts numbering at S001. (3) Append-only is not hoarding: clean sessions append nothing to the friction logs; resolved/superseded entries move **verbatim** to the log's `archive.md` (now incl. `plans/archive.md`); 3+ repeats roll up into one `Recurring` entry; `prune` reports all three — and the door-close bounds `sessions.md` per office. (4) One-way linkage is swept with `ledger-mem lint --tree` (all tracked product files, not just the staged diff), and a leak found from an earlier session is **stripped on sight** as a safe fix, never backlogged.
- **Consequences:** the roster table is now six columns (legacy four-column rows still parse; they warn to migrate); `office_size` is now a hard behavioral trigger, not just a tidy-up knob; compaction is an explicit append-only exception (relocates verbatim, never rewrites) documented in the schema's "compaction, not hoarding" subsection; this package applied the leak rule to itself (the 1.1.1 `ledger-sync` fix) and now ships the sweep that enforces it downstream. Tool parity (sh+ps1) verified over shared scratch fixtures; suite grew 22 → 34.

## ADR-6: The backlog is a capped work queue; deferred knowledge moves to a parking lot (2026-09-15)
- **Status:** accepted — shipped in core 1.2.0
- **Context:** the supervisor's diagnosis on a fleet project: its `tasks/backlog.md` had grown to 57 rows and stopped being workable — half were research findings, open design questions, deferred items, and "someday" ideas with no next step, not tasks. The header said "delete rows when done", but the culture said never lose information, so nothing left and the queue turned into a document nobody could work from. Two roles were collapsed into one file: a queue an agent acts on, and a record the project keeps.
- **Decision:** split them (the supervisor chose "Option B — cleaner"). `tasks/backlog.md` becomes actionable work only — the test for a row is "can an agent start on this and finish it?" — capped at `backlog_cap` (default 20, `workflows/history.conf`); adding a row past the cap means pruning the lowest-value open row first (to the parking lot or the bin), and `ledger-mem check` reports a warn-only nudge past the cap. A new `tasks/parking-lot.md` holds the knowledge base — Findings / Open questions / Deferred work / Someday, `P-<date>-<n>` IDs, no cap, no urgency; a parking-lot row is not a task until it grows an owner and a next step, then it is promoted to the queue. Office close re-seeds **work, not knowledge**: the fresh backlog inherits only rows with an active owner or clear next step; parking-lot content survives in the permanent record, not the queue.
- **Consequences:** MINOR (new file + new rules, backward-compatible) — a project that never writes a parking-lot file keeps working, since `check` only reads `backlog.md`. The 20-row cap is a working-set heuristic, not a hard limit; raising `backlog_cap` is allowed "only by intent" (the warn text says so). The reform dogfoods here: this office's backlog already held a single actionable row, so the split was a no-op on live data — the queue was healthy, the *template* was the bug. Tool parity (sh+ps1) verified; suite grew 36 → 41 (at-cap silent, over-cap warn-only, `backlog_cap` conf override, ps1 parity, work-not-knowledge checklist line).

## ADR-7: Common Pitfalls stays inline in each edition; the other five sections became playbooks (2026-09-18)
- **Status:** accepted — shipped in core 2.0.0
- **Context:** supervisor brief — protocol reading cost was taxing host-repo work (measured ~2,760 lines/~25-35k tokens for a plain kickoff). The plan going in assumed splitting *every* task-shaped section (Code Review Checklist, Functional Testing, UX/UI Review, Performance Review, Security Review, **Common Pitfalls**) out of the always-read edition into on-demand playbooks. Diffing the two editions' Common Pitfalls sections while implementing the split found two disqualifying facts: (1) the Ten Binding Rules cross-reference specific pitfalls by number ("Pitfall #28", "#30", "#34") and the two editions number their 45ish pitfalls **differently** — PAT-specific entries interleave in the cloud edition, shifting every number after the first insertion; (2) Common Pitfalls is disproportionately the section an agent reaches for *mid-session*, when something has already gone wrong — task-shape routing (decided before the session starts) can't anticipate that need the way it can for "is this a UI task."
- **Decision:** extract only the five review/testing playbooks to `core/rules/playbooks/` (loaded per `kickoff.md`'s Phase 4 routing table); leave Common Pitfalls inline in each edition, unextracted, as part of the always-relevant core. `functional-testing.md` merges what were separate near-duplicate local/cloud sections into one file with a labeled subsection each (the two genuinely differ — a local agent has a machine to run a dev server on); `security-review.md` folds the two editions' near-identical PAT-vs-no-PAT wording into one line accurate for both.
- **Consequences:** the edition files shrank less than the plan's original estimate (1159→958 local, 1228→1053 cloud, not the "350-500" first projected) — reported to the supervisor as a deliberate, evidence-based correction rather than silently overclaiming the cut. The real savings are the ~200 lines of duplicated `.context_ledger/` Directory documentation removed (pointer to `ledger-schema.md` instead) plus the ~110 lines of playbooks skipped whenever a task's shape doesn't call for them — both real, neither as dramatic alone as the combined original estimate implied. A future session must not "finish the job" by extracting Common Pitfalls too without first resolving the cross-reference numbering across both editions.

## ADR-8: The ps1 ports' sources stay pure ASCII; non-ASCII output is built from code points (2026-09-23)
- **Status:** accepted — shipped in core 2.0.4
- **Context:** 2.0.3 shipped ps1 ports that could not be parsed on Windows, so `ledger-sync verify` — and every gate calling it — returned 3 there. Two causes: a syntax error (a `$Label:` reference the parser reads as scope-qualified) and non-ASCII bytes that Windows PowerShell 5.1 decodes with the *system codepage* rather than UTF-8, turning an em-dash (E2 80 94) into U+201D, which the parser reads as a string terminator. pwsh 7 parses the very same bytes fine, which is how the release shipped broken from a macOS host with no PowerShell engine to try: the failure is invisible on the authoring platform and on any pwsh-only host.
- **Decision:** every `core/bin/*.ps1` source is pure ASCII, enforced by an engine-free guard inside `ledger-sync verify` (both editions) and by the package tests. Where a port must emit a character its sh twin writes as a literal — an em-dash in STATE.md or an archive header, an ellipsis in a truncated line — it builds that character from its code point (`[char]0x2014`, `[char]0x2026`), so both editions still write byte-identical artifacts. The rejected alternative was a UTF-8 BOM: it fixes 5.1's decoding too, but it is invisible in review, is silently dropped by editors that default to BOM-less UTF-8, and would leave the next instance of this class undetectable on a host with no engine.
- **Consequences:** the ps1 sources read a little differently from their sh twins (`$EmDash` where the twin has a literal) and carry a `SOURCE ENCODING` note saying why; the rule is checked by `verify` on *any* host, so a maintainer on macOS can no longer ship this class silently. Adding a non-ASCII byte to a port fails verify and the suite; the idiom is documented in the two ports that use it, in `core/CHANGELOG.md` and in `tests/README.md`. `parse_ports` also checks every engine on PATH rather than the first, so a pwsh-only-parseable port cannot pass and then fail under the 5.1 `.cmd` launchers.
