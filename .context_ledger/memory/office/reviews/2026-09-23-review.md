# Core 2.0.4 — Windows sessions can pass their exit gate again

On core 2.0.3 no Windows session could get through its exit gate. `ledger-sync
verify` exits 3 when a port under `core/bin/` fails to parse, two of the seven
PowerShell ports could not be parsed by Windows PowerShell, and every gate that
calls verify (pre-commit, integration, exit) inherited that verdict. Reported
from the glyph project, which hit it on its first migration to 2.0.3; this
session fixed the source and released it.

Shipped as **core 2.0.4** (`efb9665`), self-hosted (`651a778`), both pushed.

## What was actually broken

Three independent causes, each reproduced here with both engines on this
machine (Windows PowerShell 5.1.26100.9444 and pwsh 7.6.6):

1. **`ledger-state.ps1` did not parse on *any* engine.** Its `Get-Field` built
   a regex as `"...\*\*$Label:\*\*..."`. The parser reads `$Label:` as a
   scope-qualified variable reference — the `$env:` form — so 5.1 and 7 both
   rejected the whole file. This alone broke verify everywhere, on every
   platform that had a PowerShell engine.

2. **Non-ASCII bytes in a port are a 5.1-only landmine.** Windows PowerShell
   5.1 decodes a BOM-less script with the *system codepage*, not UTF-8, so a
   literal em-dash (E2 80 94) arrives as U+201D — which the parser reads as a
   string terminator and fails the rest of the file — while pwsh 7 parses the
   very same bytes fine. `ledger-mem.ps1` and `ledger-state.ps1` both carried
   such bytes. This is why the release shipped broken: the authoring host had
   no PowerShell to try, and a pwsh-only host cannot reproduce the failure.

3. **`parse_ports` checked only one engine, and preferred the weaker one.** It
   ran the ps1 half through `powershell` when present, else `pwsh`, so on a
   Windows box carrying both, a port that only pwsh could parse passed
   verification and then failed at runtime under the `.cmd` launchers — which
   target 5.1 on purpose.

Found on the way: **`ledger-state.ps1` wrote a plain hyphen where the sh port
writes an em-dash in five places** — the Core block's `— MISMATCH` note among
them — so STATE.md differed by punctuation depending on which port generated
it. The consumer's report assumed that was deliberate; it was drift.

## What changed

- `ledger-state.ps1`: `${Label}` instead of `$Label:`.
- **All seven ps1 ports are now pure ASCII.** Text that needs a non-ASCII
  character builds it from its code point (`[char]0x2014`, `[char]0x2026`), so
  the ports still emit exactly the bytes their sh twins emit — STATE.md and
  every other artifact stay byte-identical across platforms.
- **The rule is stated where an editor will see it**, since the next person
  to touch a port may be on macOS or Windows: a `SOURCE ENCODING` block at the
  top of every port says the file is ASCII on purpose, explains the 5.1
  codepage decode, and gives the code-point idiom; the two ports that use it
  show the pattern (`$EmDash`/`$Ellipsis`). The long form is in
  `core/CHANGELOG.md` (2.0.4) and `tests/README.md`.
- **`parse_ports` (both editions) checks every engine on PATH** and prints
  which engines and versions it used, so a failure is diagnosable at a glance
  instead of depending on which engine happened to be found first.
- **An engine-free encoding guard in both editions**: verify fails any
  `bin/*.ps1` carrying a non-ASCII byte. It runs on any host — the release this
  bug came from would have been caught by `verify` on the authoring machine,
  macOS included.
- **Four new tests** (suite 60 → 63 green): the shipped ports are ASCII; every
  engine on PATH parses every port; the sh port's encoding guard fires on a
  non-ASCII byte (rc=3); sh and ps1 write the same STATE.md.
- Both ports now emit the same punctuation in `ledger-state`, closing the
  hyphen/em-dash drift.

## Verified how

- `sh tests/run-tests.sh` → 63 passed, 0 failed (was 60/3 before the fixes).
- `sh core/bin/ledger-sync verify` → rc 0; prints
  `ps1 parse: OK (powershell 5.1.26100.9444, pwsh 7.6.6)`.
- `powershell -File core/bin/ledger-sync.ps1 verify` → rc 0. This is the
  `.cmd` launcher path and the exact command that returned 3 on 2.0.3.
- `ledger-state` run under sh, pwsh 7 and 5.1 on the same scratch office →
  STATE.md byte-identical every time (em-dashes included).
- Reproduced the original failures first: both engines rejected the old
  `$Label:` line; 5.1 rejected the old `ledger-mem.ps1` with ~25 parse errors
  where pwsh 7 was clean.
- Pre-commit gate passed on the staged release. `ledger-mem lint` (staged)
  reports rc=1 with 14 hits, all in `tests/run-tests.sh`, the package's own
  maintainer suite — the documented false-positive class for this repo
  (P-2026-09-19-1), pre-existing: that file cited `.context_ledger/` on 81
  lines at HEAD, 94 now.

## Still open

- The ps1 ports' **help and message text still diverges from the sh ports** in
  places — some dash-only, some structurally shorter usage blocks. Fixing the
  dash-only cases in `ledger-state` was required by the byte-parity test;
  doing the same across the other six ports needs a decision about whether
  byte-identical help text is a goal (parking lot).
- The consumer also reported **verify diagnosing a CRLF-only working-tree
  difference as tampering**. Not reproducible here on 2.0.4: `verify_tree`
  CR-strips before hashing in both ports, and a fully CRLF-converted core
  verifies clean under sh, pwsh and 5.1. Recorded as an open question with the
  exact evidence, since a real case would need their repro (parking lot).
- `gates.conf` in this repo has **no project commands**, so pre-commit runs
  only the universal checks and the package suite is not part of any gate
  (parking lot, with the latency tradeoff noted).
- Conduct miss, named because the protocol asks for it: I did not set
  `tasks/current.md` at session start (Step 3). The office was idle and I was
  solo, so nothing collided, but the single-slot board was empty while work was
  in flight.
